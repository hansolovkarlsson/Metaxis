# 2026-09-04

The whole project, start to finish, in one day: a notation, a tool that runs it,
nine examples, twenty-seven error cases, the records, and a repository. What
follows is why it went the way it did, including the four places it went the
wrong way first.

## The premise, and where it came from

Proto is next door and is not to be written to; it was read for prior art all
day. Its `lib/clike.pro` opens with a list of things C has that a Proto dialect
cannot take — `;` between statements, `x++`, `a[i]`, `p->f`, a lone `|`, `for`,
and `42` without a sigil — and every one of them is the same failure in a
different costume. Proto's own grammar and the grammars a Proto file declares
are drawn from **one pool of characters**. `;` opens a comment, so it cannot
separate statements. `|` delimits a block's parameters, so it cannot be an
operator. `.` `,` `:` are spoken for. A pattern's holes are written `<x>`, with
two characters that are themselves operator characters, drawn from the pool the
file is busy declaring from. Each is a reasonable local decision and together
they are a budget that runs out.

The premise here is one rule: **everything a directive says about foreign text is
inside a string, and everything outside a string is Prototype's own fixed
vocabulary.** Quoting spends nothing from that pool, because a string's
boundaries are the one thing every reader already agrees on.

Two things fell out of that rather than being designed in, and both are the
reason the day went as fast as it did. Four rule directives collapsed to one:
once words are quoted, a pattern's *shape* says whether it is prefix, infix,
postfix, circumfix or mixfix, and a pattern beginning with a hole is a led rule
while one beginning with a word is a nud rule — the Pratt distinction, read off
instead of declared. And the lexer stopped being a fixed budget, because the
header is read before the body, which is what makes `@token` possible at all.

## The first framing was wrong, and a note in `scratch/` fixed it

The first design draft kept Proto's templates: an expression in the target
language, expanded to a tree. That is the right answer for Proto, whose target
is Solveig and whose re-printer knows Solveig's precedence. The draft argued for
it explicitly, on the grounds that splicing text brings back every parenthesis
bug the C preprocessor has.

Then `scratch/notes.txt` turned out to say **language agnostic**, and `.pt` →
`.out`, and *samples for pascal, C, poem*. That kills structured templates
outright: there is no tree to build when the target is not known. Templates
became text with `{hole}` splices — and the notation got *better*, because the
rule became symmetric. Foreign text on the input side is quoted; foreign text on
the output side is quoted; the same rule read twice, across the arrow. What
looked like a concession turned out to be the thing that made the premise whole.

It also fixed the price honestly. Structured templates are strictly better at
parenthesising, so the cost went into `notation.md` under *What it costs*, with
`examples/pascal.out` checked in carrying its parenthesis noise rather than
tidied. That entry survived nine hours and was then paid off by the code
template, which is the correct life for a recorded cost.

## Six things quoting does not decide

Building the parser turned up six decisions the premise does not make, each of
which had to be settled and written down rather than patched. A hole's kind is
how far it reaches. Two holes may not sit next to each other. **A tie between a
token class and a declared word goes to the class** — which is the whole of *an
alphabetic word is not reserved*, because `div` is then a name token whose text
happens to be `div`. Comments are looked for before words. Candidates under one
leading word are tried longest first, which is the whole of the dangling else.
And a separator is wanted between two statements and not after one that ended in
a word.

The last of those arrived as a bug: `examples/clike.pt` would not parse, because
C's `for (…) { … }` carries no `;` after it. The first instinct was to put
semicolons in the example. That would have compiled, passed, and quietly made
the tool unable to read C — a failure on the first realistic input is evidence
about the rule, not about the input. It is `POSTMORTEM.md` 1.

## Hygiene was one problem and turned out to be two

`notation.md` recorded hygiene as a single gap with a single fix — either the
template gets a way to ask for a fresh name, or agnosticism costs hygiene — and
admitted in the same paragraph that the gap had been *reasoned about and not
tested*. Building the test split it.

The test is `examples/hygiene.pt` plus `tests/hygiene.sh`, which compiles the C
the example emits and runs it, so the wrong answers are numbers rather than
argument. It borrows Proto's method (`programs/digest` measures rather than
argues) and Proto's numbers: `forms.pro` demonstrates the same two failures and
records #105 and #0 for the second.

What it showed is that a template which **introduces** a name and a template
which **reaches out** for one look identical from outside and are not the same
thing. `{~t}` closes the first: the expander invents a name nobody else has, and
nothing else needs to know. The second cannot be closed this way — there is
nothing to invent, what is wanted is a way to say *the outer one*, and a
template that is a string cannot see a scope. So half of it became a feature and
half of it moved out of *Not done* and into *What it costs*, where it belongs:
it is the price of being agnostic, not an unwritten feature. Building the code
template later did not move it, which the roadmap predicted before either was
written and is the one prediction there that held.

The test is written to pin the **wrong** answer for the half that stays wrong.
That is deliberate: a test that merely failed would be switched off, and one
that pins the wrong answer has to be edited by whoever fixes it, in the same
commit. It has already been edited once, by `{~t}`.

## A reference is a test

Writing `docs/REFERENCE.md` meant checking every claim against the code instead
of against memory, and two were false: text mode tried rules in declaration
order rather than by maximal munch, and the `@use` limit counted files while
three documents said depth. Four commits and a green suite had found neither.

They could not have been found by the suite, because in both cases the code and
the *intended rule* differed and no example exercised the difference. That is
the shape a document catches and a test does not — unless somebody first knows
to write the test. `POSTMORTEM.md` 2.

## Brackets, and a question that answered a later one

Hans asked whether `[ … ]` had been chosen for a reason. It had — ISO EBNF
spells an optional part that way, braces were spoken for by templates — but the
honest answer was that the choice is a **readability** question and not a
structural one, and *that it can be* is the premise working: `[`, `(`, `{` and
`<` were all equally free, because foreign text is quoted. The same question in
Proto is painful, which is what `<x>` holes cost there.

Swapping `[ … ]` for `( … )` was offered. Then alternation came up as an
exploration, and `( a | b )` / `[ a | b ]` / `( a | b )*` made the swap clearly
wrong: the two brackets want different jobs, and spending `( … )` on grouping
would have taken the one that choice needs. So the offer was withdrawn by the
next question rather than by an argument.

Alternation itself was explored and then explicitly not wanted — *if we even
need it*. It is last on the roadmap, retitled to say so. It is kept only because
two things came out of exploring it that are worth more than the feature: the
bracket argument, and that the one honest customer for alternation — synonyms —
is exactly the case the dispatcher forbids, since a rule is found by its first
word and a leading choice means registering one rule under several.

## The second kind of template

`=> { … }` cost one character to tell from `=> "…"`: a template had always been
a string, and a string never starts with a brace. Nothing had to be reserved and
no file written earlier changed meaning. More than convenient, it keeps the
premise rather than bending it — the interpreted language is Prototype's own, so
it lives *outside* the strings, and the text it emits lives inside them.

It was built against five customers, each of which named a file already in the
tree. Four came with it. `examples/code.pt` is `examples/pascal.pt` with every
rule rewritten and the body left character for character alone, so the diff
between the two recorded outputs is the whole argument — the parenthesis noise
gone, the literal translated rather than moved. Both files stay, because the
string template's cost is now a **choice** rather than a defect: it is what a
string template costs, and what it buys is being four times shorter.

The fifth customer would not come. A rule that says it needs no separator after
it is not a property of a template but of a rule, so it landed separately as
`terminated`, and works on both kinds.

## `terminated`, and the answer that was wrong in both directions

The roadmap had listed three possible shapes and said to settle which before
writing anything. That was worth doing. The cheapest — work it out from the last
character emitted, skip the separator after a `}` — is not merely inelegant, it
is **wrong twice over**. `examples/clike.pt` reads C's braces and emits Solveig,
where a `.` is wanted between two statements however the one before ended;
`examples/groups.pt` reads the same braces and emits JavaScript, where it is
not; and C's own `struct { … };` wants the semicolon after the brace. The input
rule and the output rule are about two different languages and had to stay two
rules.

The word sits after the template, which is the one place in a rule where a bare
word cannot be a hole. So it reserves nothing, and `examples/reserved.pt` proves
it with a rule whose hole is called `terminated` and which is itself
`terminated`, four words apart.

## Text mode: an overstatement, then an over-correction

Asked what *groups in text mode* meant, the answer needed a demonstration, and
the demonstration produced garbage: two rules for a wiki link, and `[[here]]`
matched the labelled one because its hole went looking for a `|`, did not find
one before the `]]`, and took the one three words later on the next line.

That was reported as a correctness bug. **It was not**, and the retraction
matters more than the bug: `REFERENCE.md` §7 said *stops at the pattern's next
word — the first occurrence, not the last*, and that is precisely what the code
did. The rule was wrong, which is the harder kind, because reading code against
documentation finds nothing when they agree. `POSTMORTEM.md` 4.

The fix — a hole may not span *every* word still to come — was then wrong in the
other direction, and broke the next commit's own example. In
`"![" alt "](" src [ " " title ] ")"` the group's space is a later word, and an
alt text is allowed to contain spaces, so `![a cat](cat.png)` stopped matching
altogether. It did not fail loudly: text mode copies through anything no rule
claims, so the line came out looking like ordinary prose. The rule is now the
word that *closes* the rule — the one word whose arrival means the construct has
ended.

Groups themselves needed the matcher to stop being a scan. A single forward pass
cannot support an optional part, because what follows a hole is not known until
the rest of the pattern has been tried. It is a search now, with a budget — and
the budget was measured rather than guessed: 113KB of markdown, 2000 lines,
60ms, correct.

## The records, and the day's real theme

The project ran eleven commits with no journal, no postmortem and no `CLAUDE.md`
— all the documents that existed were about the *thing* rather than the *work*,
so a later session would have had `git log` and nothing else. `/project-setup`
filled that in, and `COMPLETED.md` and `POSTMORTEM.md` were written from what
actually happened rather than seeded empty, because an honest empty state would
have been a false one.

The theme, if the day has one, is **silence**. Almost every defect today was
something that did the wrong thing without saying so: a rule that did exactly
what it was documented to do and was wrong anyway; a bound that stopped an
example matching and let the text through as prose; a flag swallowed by a
lexer's lookahead so it was never set; two documents claiming a limit the code
did not implement. None was found by the suite. Two were found by writing a
reference, two by probing a feature by hand, one by a user's question. What
catches a silent failure is being made to state, somewhere a reader will check,
what the thing is supposed to do.
