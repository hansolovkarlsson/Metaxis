# 2026-09-08

## A question about the code template, and what it turned out to be about

The day opened with a question that sounded like documentation: does the
internal code language have functions. The answer is that it has procedures
and not functions, and the distinction is not a quibble. `@template name(x, y)`
is called as a statement, sees its parameters and its own loop variables and
nothing else, and emits into whatever called it; there is no `return` and
nothing to return, because `emit` already writes to one place. The only
value-returning callables are the sixteen builtins, and that list is closed:
no file adds to it, and no template is ever a value.

What the question was really about arrived next. Hans put together two things
that were already in the tree and had not been put together: `-u` may be given
more than once, and a rule may call a template that arrived in another file.
So a set of rules splits into a grammar whose every template is a single call
and a backend that is nothing but procedures, and the target stops being a
property of the file and becomes an argument to the command that reads it.
That is, word for word, what ANTLR and StringTemplate claim as their selling
point and what `prior-art.md` §3.1 was written down to survey: *a translator
may be retargeted by swapping in a new view, all without recompiling the
translator*.

The first thing to do with a claim like that is to try it, so a scratch
grammar of five rules and two backends went into a temporary directory. It
worked on the first run, and the reason it worked is the part worth keeping:
a parameter carries its hole's level, so `group(a, 60)` and `level(x)` answer
**inside** a procedure. Without that the backend could not decide its own
brackets, the grammar would have had to decide them, and the grammar would
have been making a decision about C while claiming to name no target. The
split would have been cosmetic. Calls resolving after the whole header is
sealed is what makes the flag order free, and that was checked both ways round
rather than assumed.

## The example, and the seam that moved when it was built

The write-up said the shape was reachable by a user and pinned by nothing,
which is a weaker position than an unbuilt feature, so it was built:
`lib/mini.mx`, eleven rules and no target, with `lib/mini-c.mx` and
`lib/mini-python.mx` beside it, `examples/mini.mx` as the whole file and
`tests/mini.sh` compiling the C, running the Python and requiring the same
three numbers from both. The C and the Python both came out right on the first
run, which is not the interesting part.

The interesting part is that the seam the roadmap item was written around
moved when it was measured against real files. The item claimed that
`terminated` cannot follow the backend, and the evidence for it was a scratch
C backend against a scratch JavaScript one, where the flag being on cost the
JavaScript a separator and the flag being off gave the C a stray empty
statement. When `mini` was built, neither of its backends met the seam at all:
both end a block with something that already ends a statement, a brace in C
and an indented suite in Python, so both want the same answer and the shared
flag costs nothing. A claim measured on files that no longer exist, meeting
files that do not reproduce it, is exactly the shape of the transcript that
`POSTMORTEM.md` 19 is about.

The counterexample was already in the tree, and it is the tag form's own live
customer. `examples/backends.mx` carries two templates for one `if` rule that
differ in the flag and have to: the default braces its branch and so ends a
statement, and the `tight` one writes a single statement and its semicolon and
so does not. Written as two backend files those two targets could not be
expressed at all. So the item now rests on a file the suite runs rather than
on a directory that was deleted, and it says plainly that `mini` does not meet
the seam and why.

Two smaller things came out of building it. A backend **can** own the output
separator, with `@separator … override`, but only if it is named after the
grammar on the command line, where a call is order free; one of two orders
working is worse than neither, so `lib/mini.mx` keeps the separator and every
procedure emits its own terminator, C's semicolon included. And the check in
`tests/mini.sh` that both backends define the same set of names caught the
first thing it was pointed at, which was the prose in three files calling
eleven procedures twelve.

## What is left

The item keeps its number and stays open on two things. `terminated` is the
grammar's and cannot vary by target, and the three ways out are written down
with what each costs. And a grammar file cannot say which procedures it
requires: a missing one is a good message at the call site and not a contract,
so a backend cannot be checked until something calls it and nothing says
whether two backends offer the same set. `tests/mini.sh` checks that by
reading the two files with `sed`, which is a test doing what the tool does not.

Item 16 is the day's other leaving: a page's verdict about the tree with
nothing that can see it go stale. It is written down with both shapes it could
take because neither is obviously right, and the cheaper of the two is honest
about not being a check at all.

## A question about global variables, and the answer being somewhere else

The day's last question came from outside the code: could `if`/`elsif`/`else`/
`endif` be read if the tool had global variables, so that a conditional were
four ordinary rules assigning and testing a flag rather than a bracket over
two arms? It is a good question about the right construct, and the first half
of the answer is that the variables have been there since yesterday. The store
is exactly a set of global variables written and read in body order, and
`lib/cpp.mx` already keeps three kinds of thing in it: a macro table, a
`busy:` guard against a macro that names itself, and a depth counter so that a
macro called inside another macro's body does not clobber its arguments. A
flag would cost nothing new.

The second half is that a flag cannot reach the thing that would have to move.
Text mode's default is to copy through: a rule fires where it matches and, if
none does, one character is copied and the scan moves on. A flag changes what
a rule that fires *emits*, and the text a dropped arm has to lose is text no
rule fires on, `int a;` and the rest of it. Suppressing that needs a rule that
matches every line, and there is no such rule to write: in text mode a rule
may be led by a word or by a class hole and by nothing else, so a `raw` hole
at the front is refused, and one that did lead would take each line away from
the rules that should read it. What the scheme actually wants is a mute on the
copier. And a mute that only silences `emit` would be the quiet kind of wrong
this tree exists to refuse, because a `#define` inside the dropped arm would
still run and still reach the table; a mute that is correct is a second
scanning mode with a list of the rules that keep firing inside it, and that
list is the tool learning which of a file's rules are its control flow. Today
the `raw` hole gets all of that for free, since an arm not taken is never
scanned at all. So the answer to the question as asked is no, and the reason
is worth more than the answer: it is the same wall item 15 met this morning,
a grammar wanting to say something about itself that the notation is built not
to hear.

But the question was still worth asking, because looking for where the flag
would go turned up something that had nothing to do with flags: the arms never
had to be a fixed pair. Groups work in text mode, a hole inside a repeated
group is a list a code template can loop over, and a hole stops only where the
declared brackets are balanced. A repeated group of `#elif` arms and an
optional `#else` therefore reads the whole construct, nested, with nothing new
in the tool, and the four rules that spelled the two shapes of `#ifdef` and
`#ifndef` became two. That was checked in a scratch directory before a line of
`lib/cpp.mx` moved, which is the habit yesterday's postmortem asked for, and
this time the scratch files were probes of a shape rather than a demonstration
of a defect: what they settled is that the pattern matches and that a nested
conditional's `#elif` does not end the arm around it.

**The wrong turn is the part worth keeping.** The obvious way to write the
group is to put the readable condition in it, `"#elif defined(" e:name ")\n"`,
and that shape quietly reintroduces the bug `refuse` was built for yesterday.
A condition the pattern cannot match is not an error there: the arm's hole
simply runs past it to the `#endif`, and the whole arm is taken or dropped
with an unread `#elif` inside it, which is a wrong answer with status 0. The
shape that works makes the group's word `#elif` and its condition whatever
follows, so an own-level `#elif` always ends the arm before it, whatever it
says, and is then read or refused. One inside a nested conditional is invisible
to the outer rule, because the arm's hole may not stop where `#ifdef` and
`#endif` are unbalanced, and the nested rule reads it in its turn.

That is also the distinction the thing it replaces could not make. Yesterday's
`@template no_elif` read each arm's text for `#elif` at the start of a line,
which cannot tell an own-level one from a nested one, so it would have refused
a legal nested arm; and it had a residue it wrote down honestly, a `#elif`
after a newline inside a string literal. Both are gone now, the second because
a declared class makes the scan move by tokens and a hole cannot stop inside a
string at all.

The flag did earn its place in the end, one level down from where the question
put it. At most one arm is taken, so the loop over the arms needs to know
whether it already took one, and a plain key is wrong: a conditional inside the
arm being expanded runs in the middle of that loop and overwrites it. A probe
showed exactly that, a second true arm firing after the first, before the key
was made a depth the file counts, which is what the macro arguments beside it
already do. And the condition itself is a rule rather than a piece of string
handling: `defined(NAME)` emits `1` or `0`, but only while a `cond` key is
remembered, so `defined(x)` standing in ordinary C is left as it was found and
its argument expanded, the way cc leaves it there too. Reading the condition
and evaluating it are one act, and a condition that expands to neither `1` nor
`0` is what the refusal now catches, naming what it could not read.

The oracle is the compiler, not this page. `tests/cpp.sh` diffs a chain
against `cc -E -P` on the same file, and the chain was written to have a dead
arm, a true arm, an arm that must not be reached and an `#else` that must not
either, an `#ifndef` whose arms are all false, a conditional nested in an arm
with a `#elif` of its own, a `#elif` inside a string, and `defined(A)` in
ordinary C. Three plants confirmed it fails when it should: an arm selected
without the flag, which produced two arms and a diff; and each of the two
refusals neutered, the first of which printed nothing at all for a file cc
keeps a declaration from, which is the 2026-09-07 failure reproduced on
purpose one last time.
