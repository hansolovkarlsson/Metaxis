# 2026-09-08

## A question about the code template, and what it turned out to be about

The day opened with a question that sounded like documentation: does the
internal code language have functions. The answer is that it has procedures
and not functions, and the distinction is not a quibble. `@template name(x, y)`
is called as a statement, sees its parameters and its own loop variables and
nothing else, and emits into whatever called it; there is no `return` and
nothing to return, because `emit` already writes to one place. The only
value-returning callables are the sixteen builtins, and that list is closed:
no file adds to it, and no template is ever a value.

What the question was really about arrived next. Hans put together two things
that were already in the tree and had not been put together: `-u` may be given
more than once, and a rule may call a template that arrived in another file.
So a set of rules splits into a grammar whose every template is a single call
and a backend that is nothing but procedures, and the target stops being a
property of the file and becomes an argument to the command that reads it.
That is, word for word, what ANTLR and StringTemplate claim as their selling
point and what `prior-art.md` §3.1 was written down to survey: *a translator
may be retargeted by swapping in a new view, all without recompiling the
translator*.

The first thing to do with a claim like that is to try it, so a scratch
grammar of five rules and two backends went into a temporary directory. It
worked on the first run, and the reason it worked is the part worth keeping:
a parameter carries its hole's level, so `group(a, 60)` and `level(x)` answer
**inside** a procedure. Without that the backend could not decide its own
brackets, the grammar would have had to decide them, and the grammar would
have been making a decision about C while claiming to name no target. The
split would have been cosmetic. Calls resolving after the whole header is
sealed is what makes the flag order free, and that was checked both ways round
rather than assumed.

## The example, and the seam that moved when it was built

The write-up said the shape was reachable by a user and pinned by nothing,
which is a weaker position than an unbuilt feature, so it was built:
`lib/mini.mx`, eleven rules and no target, with `lib/mini-c.mx` and
`lib/mini-python.mx` beside it, `examples/mini.mx` as the whole file and
`tests/mini.sh` compiling the C, running the Python and requiring the same
three numbers from both. The C and the Python both came out right on the first
run, which is not the interesting part.

The interesting part is that the seam the roadmap item was written around
moved when it was measured against real files. The item claimed that
`terminated` cannot follow the backend, and the evidence for it was a scratch
C backend against a scratch JavaScript one, where the flag being on cost the
JavaScript a separator and the flag being off gave the C a stray empty
statement. When `mini` was built, neither of its backends met the seam at all:
both end a block with something that already ends a statement, a brace in C
and an indented suite in Python, so both want the same answer and the shared
flag costs nothing. A claim measured on files that no longer exist, meeting
files that do not reproduce it, is exactly the shape of the transcript that
`POSTMORTEM.md` 19 is about.

The counterexample was already in the tree, and it is the tag form's own live
customer. `examples/backends.mx` carries two templates for one `if` rule that
differ in the flag and have to: the default braces its branch and so ends a
statement, and the `tight` one writes a single statement and its semicolon and
so does not. Written as two backend files those two targets could not be
expressed at all. So the item now rests on a file the suite runs rather than
on a directory that was deleted, and it says plainly that `mini` does not meet
the seam and why.

Two smaller things came out of building it. A backend **can** own the output
separator, with `@separator … override`, but only if it is named after the
grammar on the command line, where a call is order free; one of two orders
working is worse than neither, so `lib/mini.mx` keeps the separator and every
procedure emits its own terminator, C's semicolon included. And the check in
`tests/mini.sh` that both backends define the same set of names caught the
first thing it was pointed at, which was the prose in three files calling
eleven procedures twelve.

## What is left

The item keeps its number and stays open on two things. `terminated` is the
grammar's and cannot vary by target, and the three ways out are written down
with what each costs. And a grammar file cannot say which procedures it
requires: a missing one is a good message at the call site and not a contract,
so a backend cannot be checked until something calls it and nothing says
whether two backends offer the same set. `tests/mini.sh` checks that by
reading the two files with `sed`, which is a test doing what the tool does not.

Item 16 is the day's other leaving: a page's verdict about the tree with
nothing that can see it go stale. It is written down with both shapes it could
take because neither is obviously right, and the cheaper of the two is honest
about not being a check at all.
