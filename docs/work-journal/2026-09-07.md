## Session D: the grammar named from outside the file it reads

**Hans:** *Now with Metaxis can do a CPP, how could that tool now be applied
in a toolchain? Basically, can the CPP syntax definition be separated from
the files it applies to? Something like this: mx -u cpp.mx -i myprog.c -o
myprog.cc, meaning .c is with #-directives in it, and .cc is a file that's
been cleaned up and directives done?*

The question was answered before it was built, and the answering is most of
what this entry is worth. The seam was already in the code and had been for
a long time without anybody noticing what it was: `header_read` fills a
`Grammar` and hands back a byte offset, and `lex` and `expand_text` take a
buffer, an offset into it and a name to put in their messages. Nothing
anywhere required the buffer holding the header to be the buffer holding the
body. `Grammar` even carried `body_file` as a field separate from the file
the header came from, put there yesterday so that `read(path)` could resolve
beside the program rather than beside the rules. The concept the question
asked for was already named in the struct.

So the first thing done was not code. The shell already does this, and
running it is how the design got its arguments. Split `examples/cpp.mx` at
its `@end`, concatenate the header back in front of the body, run it: nine
correct lines. The semantics needed nothing. Three things went wrong, and
each of the three is a flag's justification rather than a feature request:

- A parse error on line 2 of a body under a 21-line header was reported as
  `_j.mx:23`. Wrong file, wrong line. That is the difference between a
  toolchain component and a script, and it is the only one of the three that
  would have been guessed.
- The header ends at the first line that does not begin a directive, so an
  input whose first line begins with `@` is eaten. `examples/cpp.mx` writes
  `@end` for exactly this reason, and no `.c` can be asked to.
- Both path bases move to the temporary file. The extracted header could not
  find its own `@use` and failed outright, and `read` looked for `cpp.h`
  beside the temporary rather than beside the program. Two files give two
  correct bases; one file cannot.

**The definition was chosen to need the least new prose.** `mx -u G -i F` is
exactly the file `@use "G"` with F's text as its body, so everything §3.5
already fixes holds unchanged and for free: read once by resolved path, so
several `-u` compose without colliding; nested no more than 64 deep; a used
file holds directives and nothing else. The one difference is where a
command-line path is taken from, and there is only one answer available: a
path in a file stands beside that file, and a path on a command line has no
file, so it stands beside the working directory. `header_use` is that
sentence in three lines.

**The mixtures are refused, and that is the design decision rather than the
flags.** `mx -u rules.mx file.mx` and `mx -i input file.mx` both have a
reading, and both readings are quiet: the first lets position decide whose
rules are declared first in a tool where declaration order settles which of
two rules fires, and the second leaves a body unread with no message. This
is the same question `override` exists for, one page earlier, and it gets
the same answer. Refusing them also keeps the cost to the premise bounded:
no file ever has *part* of its grammar from outside, so a `.mx` file either
carries its own header or carries none at all.

That cost is real and is written into `notation.md` rather than argued away.
The premise on the front page is that a file declares its own grammar, and
what that buys is that a file cannot be read wrong by being handed to the
wrong tool. `@use` had already conceded half of it, the rules living
elsewhere, but the file still named them. Under `-u` the input has no say at
all, and `mx -u the-wrong-rules.mx -i prog.c` is a mistake neither file can
catch. It is bought because the alternative was not a better naming scheme
but nothing: a `.c` a compiler also reads cannot carry a Metaxis header, and
that is the entire population of inputs a preprocessor has.

**`examples/cpp.mx` had to be split to be usable at all**, since a used file
holds directives and nothing else and that file had a body. The shape was
already in the tree: `lib/island.mx` holds stage 5's rules and
`examples/island.mx` is a body that uses them. The move changed no output.

Three things the build turned up that the reading had not. `-g` was reading
the input file before deciding to stop, so inspecting a grammar depended on
the file it would be pointed at; the read moved below the dump. A first
draft printed its own out-of-memory message when `xmalloc` has said that
since the beginning. And `cc` will not compile a `.i` file the same way it
compiles a `.c`, because a preprocessed-input extension turns off the
standard include search: worth knowing for anyone who reads the flags as an
invitation to name the output `.i`, and the reason the documents write
`prog.i` only where nothing then compiles it.

`tests/cpp.sh` runs the same body both ways and requires the same bytes,
then compiles the split form's output and runs it to the same nine lines,
then asks it for an include that is not there so the path base is pinned by
the path in the message. `tests/errors.sh` grew a second helper, `argv`,
because a command line that cannot be read is not a file that can be
refused: it takes no stdin and it must exit 2, and a refusal that exited 1
would look like a file being refused. `tests/island.sh` moved from six
`complain(err)` to eight and now counts the ninth separately, `complain(why)`
in `badline`, which is the evidence that the island rule matches the shape of
a call and not the name of the variable inside it. The suite is at 223 with
103 error cases.

## Session E: what "done" meant, and the statement that had no spelling

**Hans:** *Is the CPP basically done? No open task?*

The roadmap said yes and the roadmap was right about itself: item 11 is
retired, stage 6 is marked done, and none of the five items still on the
page is cpp-shaped. But "done" there means *the list item 11 wrote down is
read*, and the question being asked was a different one. So the seven things
`lib/cpp.mx`'s own note says it does not do were run rather than reread.

Six of them degrade **visibly**, and that is the design rather than luck:
text mode copies through whatever no rule matched, and a C compiler with a
preprocessor of its own stands behind these rules, so `#if N > 1`,
`#  define X 5` and `#include <stdio.h>` all come out the other side for
somebody who can read them. The note had listed all seven the same way, as
things not read, and that flattened a real difference.

`#elif` is not like the other six, because it stands **inside** a construct
these rules do read. An arm is a `raw` hole running to its `#endif`, so
`#ifdef B` / `int b;` / `#elif defined(A)` / `int a;` / `#endif` with `B`
undefined is one match whose arm is dropped whole, `#elif` and all. `cc -E`
keeps `int a;` and this printed nothing, with no message and status 0. A
wrong answer, not an unfinished one, and the suite could not have seen it:
`tests/cpp.sh`'s oracle only compares on a body that has no `#elif` in it.

**The fix wanted a statement the language did not have.** Refusing looks like
it should be free, and in an expression-mode file it nearly is, since a
construct no rule reads stops the parse. In text mode it is not available at
all: having no rule for a thing *is* how a file says pass this through, so
the same silence cannot also mean *I must not touch this*. The two spellings
left were a wrong answer or a rule that emits something and hopes. `refuse`
is one row in `STMT[]` and five lines in `run()`, and it takes its two static
messages from the shape `contribute`, `remember` and `forget` already had.
Its message is entirely the file's: the tool has no opinion about what a file
could not read, and inventing one would have been a second place to keep the
wording right.

**Refusing it took two rules, and the reason is the feature working.** A
dropped arm is by design never scanned, so a rule matching `#elif` inside one
could never fire: that is `raw` doing its job, and it is why a `#define` in
an untaken arm does not fire either. So a `@template no_elif(a)` reads each
arm for a `#elif` at the start of a line **before** either is taken, and a
plain rule catches one standing outside any conditional. Checking for a line
start rather than the bare word is what keeps `puts("#elif")` passing, and
the residue, a newline followed by `#elif` inside a string literal, is a
refusal rather than a wrong answer, which is the direction to be wrong in.

The lesson is about the question and not the code. A retired roadmap item
says a list was read; it does not say the thing is finished, and the only way
to tell the two apart is to run what the file admits it cannot do and look at
*how* each one fails. Six failed safely and one did not, and nothing on any
page distinguished them, because the note that listed them was written by
whoever built them and had no reason to. The suite is at 226 with 106 error
cases.

## Session F: the stale count, and the lesson applied a second time

Two pages had gone stale on the same number. `README.md` said "the nine
scripts in tests/, six of which run what they produced" and
`docs/notation.md` said six and four. There are ten, and seven of them run
what they produced: `asm`, `basic`, `cpp`, `hygiene`, `island`, `pascal` and
`python`, counted by looking for a compiler or an interpreter in each rather
than from memory. `scale.sh` calls `python3` and is not one of them, because
it uses it as a millisecond clock and never runs what it produced.

Neither sentence was wrong when it was written, which is the whole shape of
the thing. `CLAUDE.md` said ten and was right, so the tree already disagreed
with itself in two places and nothing could see it.

**This is POSTMORTEM 16 exactly**: a number in prose is not a check, first
written about `docs/COMPLETED.md` claiming "all six places the suite runs the
tool" when there were seven that morning and eight by the evening. Check 1 in
`hygiene.sh` answered that one by *stating a property instead of counting*,
which is the better move where it is available. It is not available here:
"the ten scripts in tests/" is a number a reader wants, and removing it to
make it uncheckable would be losing information in order to avoid a check. So
the number is checked. The count is read off the Makefile, which is the only
thing that decides what `make check` runs, and every page that states one
must agree.

Two details worth keeping. The pages are **joined into one line before the
phrase is looked for**, because `README.md`'s claim is wrapped across two
lines and written down the left of a fenced block behind `#`; a line-based
grep would have seen neither half. And the phrase looked for is a number word
immediately before `scripts in tests/`, not `scripts` alone, which is what
lets `prior-art.md`'s "most of the scripts in tests/ run" stay prose and
`COMPLETED.md`'s "verified at ... nine scripts" stay a state on a day. A
check that held those to today's count would be wrong about both.

Three plants confirmed it fails when it should: `README` saying nine, which
is the wrapped one; `CLAUDE.md` saying twelve; and a script leaving the
Makefile, which is the direction that actually happens, and which named all
three pages that then needed editing. The suite is at 227 with 106 error
cases.
