# 2026-09-05 — the day it stopped being a rewriter and started being aimed

The second working day. It began with two roadmap items that were meant to be
small and ended with a document about what the tool could become, and the
distance between those two things is the shape of the day. Three of the four
turns in it were taken because somebody said "actually, not that" — twice Hans
and once a compiler — and the record is more useful for those than for the
features.

## The last silent wrongness, and where a check belongs

Roadmap 1 was a class-kind hole under `@mode text`: `@syntax "[" x:name "]"`
took everything up to the `]` and never consulted the kind. The roadmap offered
two answers, honour it or refuse it, and recommended refusing.

Refusing was right, but the interesting question turned out to be *which kinds*.
`expr` and `stmts` both mean **read up to the word that stops you**, which is
precisely what a text-mode hole already does, so those degrade honestly and
should be left alone. A class kind says something else — *one token, matching
this regex* — and text mode has no tokens at all to say it about. So it was
never a kind being approximated; it was a kind being ignored while the file went
on looking correct. That distinction is why only the class kind is refused, and
it is the whole justification for the rule.

The part worth keeping is **where the check runs**. The obvious place is the
rule that declared the hole. That would have been wrong, and not subtly:
`@mode` is a directive like any other, so a rule can be written *before* the
mode is, or arrive through `@use` from a file that names no mode at all.
Checking inside `@syntax` would have caught the file that happens to declare its
mode first and let the other two through — the same silent pass, one
directive-order away. The check moved to `grammar_seal`, which runs once the
header has finished speaking and the mode is settled, and all three orderings
were then verified by hand rather than assumed.

`grammar_seal` gained an error path for it. That turned out to be where the next
thing needed to live too.

## A roadmap item that described its own defect backwards

The next item was *two files declaring one word*, and the standup was explicit
that the answer was Hans's to pick and not mine. So the morning went on
investigation instead, which is how the item's own description turned out to be
wrong.

It said: `@use` two files that both declare `"+"` and **the later one wins,
silently**. That is true of `@token` and `@separator`, which replace in place.
For a *rule* it is the opposite. Candidates under one leading word are tried
longest-pattern-first with declaration order breaking a tie, so the **earlier**
wins and the later is unreachable — the file that wrote the second template
gets the first one's output and nothing says so. Both orders were run to be
sure. Had the fix been built to the description, it would have been built to
make the later win, which it already did in two cases out of three and never did
in the one the example was about.

The second finding was worse and had to be fixed first: `@use` read a file once
*per route to it*, so `a` and `b` both using `base`, with one file using both,
declared everything in `base` twice. That is a file colliding with itself over
declarations nobody wrote twice, and any collision rule would have fired on it
before it ever saw a real one. Proto reads once for exactly this reason; so does
this now, identity being the resolved path.

Hans chose *let a file say which it meant* over Proto's *later wins and the
compiler says so*. That was the right call for a reason beyond taste: Proto's
answer needs a warning channel this tool does not have, it would have flipped
rule resolution from earlier-wins to later-wins, and it decides by position
something this tool declines to decide by position everywhere else.

**The word could only go in one place, and the notation put it there.** Left of
the `=>` a bare word is a hole — the premise everything rests on — and a rule
whose first hole is called `override` is a legal rule. After the template there
is no pattern, so a bare word cannot be anything else; `terminated` was already
there for exactly that reason. The premise decided the syntax rather than being
bent around it, which is the case it is supposed to earn its keep on.

Testing that turned up a smaller thing worth having: `@token name "…" garbage`
had always been accepted with the extra word ignored, which was harmless until
the directive took an optional bare word, at which point `overridden` would have
been read as `override` with three characters dropped in silence. Both `@token`
and `@separator` now refuse trailing text, as `@syntax` always had.

## The reference, and a page that said it was checked

Hans asked for Solveig to stop being the output language in `REFERENCE.md` — a
reader of Prototype should not have to learn Solveig to see what Prototype did.
Straightforward, and it is now C and Pascal throughout, with Solveig surviving
only in the Proto comparison where it is a fact about Proto rather than an
example anybody must read.

The audit attached to it is what mattered. Seven directives, seven builtins,
every error message in `prototype/src`, every limit and every section
cross-reference, checked against the code rather than by eye. Two were stale.
And then **§ 1 — the first thing anybody reads — did not run**: nothing in it
declared `=`, and it gave `;` to both `@comment` and `@separator`, where
comments win, so the separator could never have fired either. The output printed
beneath it was what the file would have produced if it had worked.

It was the only whole file on the page and the only one that could ever have
been run, and it was the one written by hand instead of lifted from `examples/`.
It is now `examples/first.pt` with a recorded output. The page had also claimed
*everything here is checked by `make check`*, which was true of the behaviour it
describes and false of the examples in it, and that sentence is why the defect
could sit there: a claim of verification reads as provenance rather than as an
assertion, so it is trusted in precisely the place a sceptical reader would
otherwise have looked.

## The turn: one translator at a time

Then Hans changed the frame, mid-task, and the new frame was better than mine.

I had proposed Python-in and C-out as the standing pair, having checked that
Python's blocks were unreachable and said so. Hans replied that focusing on one
conversion at a time — Pascal→C now, C→assembly next, something else after —
would let mechanics be introduced and tested properly. That is a stronger idea
than the one it replaced, and for a reason worth writing down: **it makes the
tree's existing test for whether a surface has earned its place into a
schedule.** One translator, taken far enough to be compiled and run, so that
every feature added has a customer that asked for it before it was built.

My framing had been answering the wrong question. I had been asking *which
languages should the examples use*, which is a matter of taste; Hans was asking
*where should the pressure come from*, which is a matter of method. The Python
example I had half-written was deleted rather than landed, because a file that
says Python and cannot write an `if` claims more than it does.

Two claims of mine did not survive contact with the same conversation. I had
written in the roadmap that `terminated(h)` would help the string form too; it
cannot, because a string template has no way to emit conditionally, and it is a
code-template builtin exactly as `level` and `group` are. And the reference's
new promise — *every example here emits C or Pascal* — was one target wide,
written an hour earlier under the narrower plan, and a page about a
language-agnostic tool that only ever shows one language argues the opposite of
what it says. The constraint that was actually meant is that the output is
always a language the reader already has.

## Stage 1, and the compiler earning its place immediately

`examples/pascal.pt` was already Pascal→C, so stage 1 had a foundation. What it
did not have was any way to know whether the C was right:

```
$ pt examples/pascal.pt | cc -xc -
error: use of undeclared identifier 'total'
```

Pascal declares its variables and the example had no rule for `var`, so the
output assigned to names C had never heard of. Nothing caught it because
`pascal.out` is checked by `diff`, and `diff` does not compile anything. That is
the argument for a C target restated as a defect in the tree that made it.

`var` itself needed no new machinery, which was the useful thing to learn about
the stage: a type is a quoted *word* rather than a `name` hole, because a hole
splices the token it matched and `integer` has to come out as `int`; `,` is an
ordinary infix rule at 20 and `:` one at 15, so `total, mod: integer` parses the
way it reads; and `var` is a rule that does nothing to what follows it.

Then `tests/pascal.sh` started compiling and running the output and checking the
number it printed, and it paid on the first run. Both example files had been
emitting `if (c) x = 1 else x = 2`, which is not C — a branch that is an
expression wants a `;` before the `else` and a branch that is a block must not
have one. Wrong since the day they were written, green in every recorded output
the whole time, because it was plausible. Later the same test found that a
block's last statement had never had a semicolon at all, since a separator goes
*between* statements and never after the last, and `begin … end` closed straight
over it.

## Two mechanics, both asked for rather than guessed

Bracing every branch unconditionally fixed the first of those, and named the
mechanic that would remove the braces. Which of the two a branch is depends on
the rule that filled the hole, and that is exactly what `terminated` already
records — per rule, tracked through the parse. A template could not ask.

**Nothing had to be computed; something had to stop being thrown away.** `Out`
returns `{ level, terminated }` from `p_expr` and only `level` reached
`bind_put`. `Bind` gained the field beside `level`, `Val` gained it beside
`level`, and the builtin reads it the way `level` does. The shape of that is the
point: a question a template could not ask was one field of plumbing rather than
a new idea.

`procedure` and `function` then needed nothing at all, which is what the
roadmap had predicted about the whole stage. The interesting part was the return
value: standard Pascal returns by assigning to the function's own name, and that
is not reachable here, because the `:=` inside a body is an ordinary rule and
nothing tells it which function it is inside. A rule sees its own pattern and no
context at all. So the example reads Free Pascal's `Result`, and says why.

And here I overclaimed and the recorded diff caught it. I had written in both
files that the code template's loop over a parameter list could do something
`join ", int "` could not. It cannot — both produce identical `(int a, int b)`,
because every turn needs the same word in front of it. The comments now say the
useful version: `join` is the special case, a loop is the general form, and the
special case is common enough to reach for first.

**`case` was the one the prediction got wrong.** Its arms want to be a repeated
group of `[ v ":" s ]`, and they cannot be: two holes in one group come out as
two **parallel lists**, and nothing pairs them. A code template's `for` walked
one list with no index; a string template splices each of them joined. The
workaround is to fold the pair into one value with an infix `a ":" s` rule
before the group ever sees it, which works and is not general — it needs the two
parts to be joinable by an operator, and it only parses because
`a ":" "integer"` happens to be declared above it. A rule whose correctness
depends on the order of its file is what the absence of one builtin was costing.

So `for i, x in h` and `at(h, n)` were built, and `examples/code.pt` now writes
its arms as the grammar describes them while `examples/pascal.pt` keeps the
workaround — the fifth and sharpest difference between the two files.

**The bug in that one was mine and it hung.** A loop with an index puts two
frames on the environment, and my restore said `ev->env = fi.up`, which is the
*first* frame rather than what was there before both. The second turn linked a
frame to itself and `lookup` walked a cycle forever. It surfaced as a test
hanging rather than as a wrong answer, which is the one kind of failure a tree
of recorded outputs cannot express: there is no `.out` for *did not terminate*.

Midway through the `override` work the whole suite went red at once and I said

Two things came out of it. Comparing against `HEAD` is `git archive` into a

## What the day was actually about

The last hour was Hans asking what Prototype could become, given that Phoenix
already generates compilers and Futamura already describes machines, and that
Prototype is bottom-up where EBNF is top-down.

The answer that survived scrutiny is in [direction.md](../direction.md), and the
part of it that came from the day's work rather than from theory is this. Every
limitation hit today reduces to one sentence — **a rule sees its own pattern and
nothing else** — and none of them would have been helped by adding grammar.
`Result :=`, the uncallable parameterless procedure, `writeln`'s argument types,
`real`, hygiene's reach-out half: all context, not structure. Meanwhile the
three things that *were* missing structurally — a reusable parameter list, an
arm that is two holes, a `var` group with two types — want named pattern
fragments, which is a much smaller idea than a recogniser grammar.

That is why the page says Prototype is a bottom-up attribute grammar whose
attribute type is fixed at text, and why the two ways to grow are richer values
flowing up and a file-declared store flowing down. It is also why reading C
properly is declined in writing: C's hard part is not its grammar, it is that
`x * y` cannot be parsed without knowing whether `x` is a typedef, and that is
the same wall as everything in the table.

That was where the day was closed out, at ten commits. It did not stay closed,
and the rest of this entry was written in a second pass — five more commits, and
the most instructive hours of the day, because three of the things below were
predictions that had been written down that morning and turned out to be wrong.

## Naming the thing before it was true

The first of the five was a paragraph rather than a feature. Hans asked whether
*a generic interpreter generator, meant to prototype a new language* was a fair
one-line description, and the honest answer was half. *Meant to prototype* was
right — with **notation** rather than language, since `examples/poem.pt` turns
prose into HTML and that is a notation with no `if` in it. *Interpreter
generator* was not: the tool emitted text and nothing it produced ran.

What went into `direction.md` was therefore the phrase, dated, kept in a table
beside what was true instead, and a statement of the one thing that would make
it true. The reason for writing it down before it was true is the reason
POSTMORTEM 9 gives: a claim shaped so it can be wrong in public teaches
something when it is, and a claim that drifts into truth teaches nothing. It was
wrong in public within two hours.

## The arithmetic experiment, and the test nobody had written down

`+` in a code template had always concatenated, and there was no way to read a
hole's text back as a number. Adding `-`, `*`, `/`, `%` and `num(h)` was an
afternoon's smallest possible change, and it did what it was meant to:

```
2 + 3 * 4      →      14
```

`examples/calc.pt` is the first file here with no target language. Nothing about
the tool made that possible except the arithmetic — a rule has always taken the
values its children produced and combined them into its own, and the only change
is that the combining may now be `*` instead of concatenation. Seeing that run
is worth more than the phrase *bottom-up attribute grammar* had been.

**The question the experiment was given was whether it would read well**, and it
does; `num` on every operand is the only noise, and it is deliberate, because
reading a number out of text that merely looks like one is the coercion this
tool refuses everywhere else.

**The question it actually answered was a different one.** A conditional was
added to see how far it went, and it selects correctly, and:

```
if 1 then 10 else (1 / 0)      →      pt: '/' by zero
```

A hole is filled by parsing and expanding its subexpression *before* the
template runs. So a rule can choose between two values that have already been
computed, and cannot leave one uncomputed. Evaluation is eager and cannot be
otherwise, and every construct an interpreter needs that a calculator does not —
a short circuit, a loop, a recursion — is a thing that must *not* happen. What
arithmetic bought is exactly an evaluator for expressions, and the gap to an
interpreter is not an operator but **deferral**.

So the naming section written two hours earlier was rewritten rather than
appended to, as that page's own note promises. It had priced the gap at one
roadmap item and been wrong, and it had named *reading* as the risk when
reading was fine. Being wrong in the predicted way would have taught nothing;
being wrong in a different way is the whole return on writing it down.

## Stage 2, and a target that is not shaped like its input

C to arm64. The question was whether the output side generalises past targets
that nest the way the input nested, and it does. A Pascal expression becomes a C
expression one node at a time; assembly is a sequence, so an expression becomes
a run of instructions leaving a value somewhere agreed, and the value a rule
passes up stopped being *the phrase* and became *the code that computes the
phrase*. **Nothing in the tool had to change for that**, which is the strongest
confirmation the attribute-grammar framing has had.

The discipline is a stack machine, every rule's output being code that leaves
one value pushed. `tests/asm.sh` assembles it, links it against a four-line
runtime and runs it, so `14 90 10 20` is checked by a CPU.

Two things it cost. **A literal is not code**: `3` is a bare token, a rule cannot
match a bare token, so nothing turns it into `mov x0, #3`. `level(h) == 1000`
distinguishes a literal from a subexpression, which works and is the same
limitation `examples/pascal.pt` meets when it cannot translate a string —
arrived at from the leaves of a code generator instead of from inside a call.

**And a label is needed twice**, at the branch and at the place it jumps to.
`fresh("L")` returned a different name on every call. The reference said `fresh`
and `{~t}` were *the same thing*; `{~t}` was memoised per application and used by
two examples and a compile-and-run test, and `fresh` had never been used by any
file in the repository. The unexercised half had drifted, and the sentence
asserting they were the same is what stopped anyone looking. POSTMORTEM 10 is
about that: an equivalence claim is a test nobody wrote. The audit it recommends
was then run, and every builtin in the reference's table now has at least one
example using it.

## The repetition that asked for a directive

`examples/asm.pt` wrote the same two lines at every operand — the test that
tells a literal from a subexpression — eight times, identically, because **this
tool could name a rule and nothing else**. That is what `@template` was built
for, and it is the second half of a gap `direction.md` had already described from
the pattern side without knowing the template side existed.

It is called as a statement and emits into whatever called it, because `emit`
already writes to one place and a return would have been a second mechanism for
nothing. Its body sees its parameters and not the caller's holes, which is the
difference between a named fragment and a macro and is what lets it be read on
its own. Calls resolve at seal, for the third time this week and for the reason
that keeps coming back: the order a file writes its directives in should not
change the answer.

**And it settled the question that was open when it was proposed.** Named
pattern fragments and named template fragments are two mechanics and not one. A
template is called at expansion, takes arguments, has a scope and can recurse; a
pattern fragment is spliced at declaration and has none of those. Building the
first is what made that obvious, and no amount of thinking about it beforehand
had.

What it bought was measured rather than asserted, because two claims of mine had
already been refuted by measurement today: the rules section went from 2458
bytes to 1473 and **gained three lines**. Lines are the wrong unit and saying so
is better than picking the flattering one. The expansion is byte-identical to
what the file emitted before, which is what makes it a refactor rather than a
rewrite.

## What the afternoon was actually about

Four predictions met evidence in one day. The staging held, twice over, and
produced two mechanics with customers that asked for them. `case … of` needs no
new mechanics: wrong. Arithmetic makes this an interpreter generator: wrong.
Named fragments are probably one mechanic: wrong. Three failures out of four,
and every one of them produced something — the failures are where the roadmap
items came from, and the one that held is the only one that produced nothing new
to write down.

That is the day's lesson and it is not about any of the features. **A prediction
is worth writing down in proportion to how cheaply it can be shown wrong**, and
the cheapest way to show one wrong is to build the smallest thing that tests it
rather than to reason about it. Every wrong prediction today was refuted by a
file: `examples/calc.pt` for the interpreter claim, `examples/asm.pt` for both
of the others. None was refuted by argument, and one of them — the reading risk
the arithmetic item had named — was argued about at length and turned out not to
matter at all.

Fifteen commits, all pushed. The tool gained a refusal, `override`, four
builtins, arithmetic and a directive; the examples gained two stages and three
files; and the records gained a fourth document that has already been rewritten
twice by its own evidence.

That was the second close-out. The day did not stay closed either time; what
follows is a third stretch, and it is one feature and one argument about where
to put it.

## `@fragment`, and the slot it was nearly written into

Roadmap 1 was the pattern half of naming a fragment, and the standup called it
*small, no open design questions*. It had one, and the roadmap had hidden it by
writing the answer down early: `direction.md` sketched `@kind params = …`,
spliced as `p:params`, and never said what the `p` bound to. It could not, and
that is the whole of what this stretch was about. A fragment declares holes of
its own — `[ p:name ":" "integer" ]* sep ";"` declares `p`, and the rule's
template splices `{p}`. So `p:params` is either a hole name that shadows the
fragment's, or a rename that caps a fragment at one hole, and neither had been
chosen.

Three spellings were on the table and one of them dies immediately. **A bare
`params`** cannot work: a bare word in a pattern is a hole, so whether `params`
means *a hole called params* or *splice the fragment* would depend on whether
the `@fragment` had been declared yet. That is order-dependent meaning, which
this tree has refused three times this week for the same reason.

**`p:params`** — the sketched one — was refused on the ground that it caps a
fragment at one hole, and the roadmap already names the customer that breaks it:
Pascal's `real` beside its `integer` puts a *type* in the parameter list, which
makes the fragment `[ n:name ":" t ]*` with two holes. `direction.md`'s own
example had two holes. The spelling it proposed could not have expressed the
example it proposed.

**`@params`, in a namespace of its own**, is what was built, and the argument
for it is one the tree had already made one level up. A *kind* answers what one
hole holds; a fragment answers what sequence of elements goes here and arrives
carrying holes. Writing both after a `:` is one position meaning two unrelated
things — which is exactly why `@template` and this were split into two
directives in the first place. The same argument applies to the splice site, and
applying it consistently is what named the directive: `@fragment` is the word
this page and the roadmap had both been using in prose for two days while
calling it `@kind` in the code fences.

**What that bought, beyond reading better.** Kinds stay `{expr, stmts, text,
class names}`, so roadmap 3 — refusing those three names at `@token` — is still
two lines instead of growing to cover fragment names. And the kind slot stays
free for something that would actually be a kind, which stage 3 may well want
when Python's blocks arrive. Neither of those was the reason for the choice;
both fell out of making it for the right reason, which is the usual sign.

## What it cost, and the refusal nobody had asked for

The feature is small: elements are copied into the pattern at the point the
rule is declared, and from there nothing downstream knows a fragment was
involved — the rule is checked, sealed, matched and clashed as one pattern.
Requiring a fragment to be declared before it is spliced comes free with that,
and it pays twice: a fragment cannot splice itself, so no cycle is expressible
and no depth guard was needed, and there is no order in which a file could have
meant something else.

Two things did not come free.

**`override` had to go before the `=`**, which is the opposite of every other
directive here and was not a choice. Everywhere else the word goes last, because
after a regex or a template is the one place a bare word cannot be part of the
thing being declared. A fragment's pattern runs to the end of the directive, so
there is no such place: a trailing `override` reads as a hole called `override`.
The word exists to stop a silent misreading and would have caused one.

**And a pattern that declares one hole name twice is now refused.** `bind_put`
fills the first hole it finds by name, so the second could never be reached —
silently. Nothing in the tree had ever written one, which is why nothing refused
it; splicing one fragment twice into a rule is two of every hole it declares,
which turns a mistake nobody made into one that is easy to make by accident. So
the check landed with the feature that asked for it, and it refuses the
hand-written case too. That the whole suite stayed green when it was added is
the evidence that nothing was relying on the old silence.

## The measurement

`examples/pascal.pt` and `examples/code.pt` each wrote one parameter list twice.
Each now writes it once, and **both expand byte-identically to what they
expanded to before** — which is what makes this a refactor rather than a
rewrite, and is the same standard `@template` was held to this afternoon.

The lesson is the one from POSTMORTEM 11 arriving a third time in a day, from
the other direction. That entry said this page gets *shapes* right and
*distances* wrong. Here the roadmap got the shape right — named pattern
fragments, spliced, not a recogniser grammar — and got the **spelling** wrong,
having written it down as settled. A sketch in a plan document is a prediction
like any other. This one was cheap to refute because there was a file that had
to be written in it.

## The dedup that found a crash

`examples/code.pt` still wrote the same four-line body twice after the fragment
landed — `procedure` and `function` differed only in C's return type — and
sharing it is what `@template` is for. So the two mechanics meet in one file:
`@params` shares the pattern, `subprogram` shares the body, and the return type
is the argument.

Writing it segfaulted. Not on the input — at **seal**, before a line of the
program was read, and on the previous commit too. `@template` shipped yesterday
with `for` legal in a template body, and `check_block` calls `rule_has_hole` to
refuse a loop variable that shadows a hole. A template has no rule and no holes;
it is passed `NULL`, which `check_expr` in the same function guards for and the
`for` branch beside it did not. Any template that looped crashed, and none ever
had, because `examples/asm.pt` — the file that asked for `@template` — has eight
call sites with nothing to loop over.

**That is the lesson and it is not about null pointers.** A feature is tested
only to the depth of the file that asked for it. Building what a customer asked
for is still the right rule and is why this tree has no unused surface; what it
does not do by itself is *cover* what got built. Everything `asm.pt` did not
walk shipped unexecuted, and one of those branches was a crash that a compiler
would not catch and a diff could not see. POSTMORTEM 12 has both halves.

It is fixed, and the pin is the example rather than an error case: `code.pt` now
goes through `tests/pascal.sh`, which compiles the C and runs it, so a CPU
checks that the template loops. That is the third time this week a test that
*runs* the output found something the recorded `.out` beside it had been passing.

Both files still expand byte-identically to what they expanded to this morning.

## The last silent shadowing

Roadmap 3, and it was two lines as advertised: `@token expr`, `@token stmts` and
`@token text` are refused, because a hole's kind resolves against those three
names before any class is consulted. A class called one of them was accepted and
then never used — `expr` silently, and `text` by way of an error about `@mode`
that named a mode the file need not have mentioned.

It is worth writing down only for what it did *not* cost. This item was on the
page before `@fragment` was built, and the obvious spelling for a fragment —
`p:params`, in the slot after a `:` — would have put fragment names into exactly
this namespace and turned a three-name check into one that had to know about
every fragment in the file, in a file that may `@use` others. Choosing `@name`
for the splice was argued this morning on the grounds that a kind and a fragment
answer different questions; that it also kept this item at two lines was not
part of the argument and is the sort of thing that falls out of getting the
first reason right.

Three of the tool's silences are now refusals — a rule's pattern declared twice,
a hole name declared twice, and a class named after a kind — and the remaining
one on the page is `@mode`, which is roadmap 4 and needs a decision rather than
a rule.

## Two files the renumbering did not reach

Inserting `@fragment` as REFERENCE.md § 3.9 pushed `override` to § 3.10, and the
sweep for stale cross-references covered REFERENCE.md and stopped there.
`notation.md` and `ROADMAP.md` both still pointed at § 3.8, and ROADMAP's
sentence also still said three things can be declared twice when there are now
five. Both were found by grepping for the old number *outside* the file that
moved it, which is the check that should have run in the first place.

Small, and worth a paragraph only because it is the same shape as the day's two
larger findings: a change was verified where it was made and not where it was
referenced. The suite could not have caught it — nothing here tests prose
against prose — so the honest note is that cross-references between documents
are unchecked, and the only thing standing behind them is remembering to grep.

## What the close-out found, which is the point of doing one

Writing this entry is what found that `notation.md`'s directive grammar was two
directives stale. It never gained `@template` yesterday and would not have
gained `@fragment` today, so the one document whose job is to argue *why the
notation is shaped this way* had a grammar that no longer described the
notation. It has both now, along with the argument for why they are two
directives rather than one.

It also found that the page's entry on where `override` goes had become half an
answer. That entry says the word can only sit *after* the template, because
everywhere left of the `=>` a bare word is a hole. `@fragment` obeys the same
premise and is forced to the **opposite** end — its pattern runs to the end of
the directive, so there is no after — and one word now appears at two ends of
two directives with neither position chosen. That is a better statement of what
the premise costs than the original had, and it existed only because two shapes
disagreed.
